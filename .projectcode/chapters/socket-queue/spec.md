# socket-queue 소켓 메시지 큐 (선택)

종류: 기능
배울 것: 발행기를 바꿔 끼우기

## 할 일
- S1 소켓 발행기는 이벤트 발행기 자리에 그대로 들어간다. 결제 완료 메시지 글자는 받는 쪽 포트로 소켓을 열어 한 줄로 보내고, 주문 접수됨 같은 다른 이벤트는 지금처럼 발행기 안에 모아 두었다가 처리할 때 구독자에게 넘긴다
- S2 소켓 받는 곳은 정해진 포트를 열고 기다리다가 들어온 메시지 한 줄을 돌려주고 포트를 닫는다
- S3 배송 앱(받는 쪽 main)은 9090번 포트에서 기다린다고 알리고, 받은 메시지를 보여준 뒤 지금의 결제 완료 메시지 처리기에 넘겨 배송을 만들고 1번 주문의 배송을 보여준다
- S4 주문 앱(보내는 쪽 main)은 이벤트 발행기 자리에 9090번 포트로 보내는 소켓 발행기를 넣어 주문 응용 서비스를 만들고, 김철수가 자바 책 2개와 볼펜 1개를 서울시 강남구로 주문하고 결제한다. 결제 완료 메시지는 다른 프로그램인 배송 앱이 받는다

## 실행 결과
배송 앱 (먼저 실행)
배송 앱이 9090번 포트에서 메시지를 기다립니다
받은 메시지: ORDER_PAID|orderId=1|address=서울시 강남구
배송 컨텍스트: 1번 주문, 서울시 강남구

주문 앱 (배송 앱이 기다릴 때 실행)
주문 앱을 시작합니다
결제: 1번 주문, 결제 완료
결제 완료 메시지를 배송 앱으로 보냈습니다

Main은 앞 장 출력 서른세 줄 그대로다.

## 메시지
ORDER_PAID|orderId=1|address=서울시 강남구
- 앞 장의 결제 완료 메시지 글자 그대로다
- 소켓으로는 이 글자 한 줄 뒤에 줄바꿈을 붙여 보낸다

## 흐름
주문 앱 결제하기 -> 공개 호스트 서비스가 결제 완료 메시지를 발행기에 넘김 -> 소켓 발행기가 9090번 포트로 한 줄 보냄 -> 배송 앱 소켓 받는 곳이 한 줄 받음 -> 결제 완료 메시지 처리기 -> 배송을 만들어 저장

## 그대로인 것
- 주문 컨텍스트의 도메인, 주문 응용 서비스, 공개 호스트 서비스는 바뀌지 않는다
- 배송 컨텍스트의 배송, 배송 저장소, 결제 완료 메시지 처리기는 바뀌지 않는다
- Main 장면과 출력은 바뀌지 않는다. 같은 프로세스 안 발행기를 그대로 쓴다

## 안 하는 것
- 배송 앱이 메시지를 여러 개 계속 받기: 안 만듦. 메시지 하나를 받고 끝난다
- 받는 쪽이 꺼져 있을 때 메시지를 모아 두었다가 다시 보내기: 안 만듦. 실제 메시지 큐 제품의 일이다
- 같은 메시지를 두 번 받을 때 배송을 한 번만 만들기: 미룸
- 용어집 줄: 더하지 않음. 소켓과 포트는 업무 말이 아니다
