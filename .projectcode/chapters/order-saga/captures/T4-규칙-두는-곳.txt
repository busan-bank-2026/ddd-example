# 규칙 두는 곳 정리

새 규칙이 생기면 이 문서에서 둘 곳을 고른다.

## 규칙 두는 곳

| 두는 곳 | 두는 규칙 | 이 프로그램의 예 |
|---|---|---|
| 값 객체 | 값 하나가 늘 지켜야 하는 것 | Money는 0원 이상이다. Address는 비어 있지 않다 |
| 애그리거트 | 한 애그리거트 안에서 늘 함께 맞아야 하는 것 | Order는 항목이 하나 이상이고 주문 금액이 항목 합과 같다. OrderStatus가 상태가 바뀌는 길을 정한다 |
| 도메인 서비스 | 두 애그리거트 이상을 읽고 계산만 하는 것 | DiscountPolicy는 회원 등급과 주문 금액으로 할인 금액을 낸다 |
| 명세 | 참 거짓으로 답하는 조건 | FreeShippingSpecification은 50000원 이상이고 제주가 아니면 무료 배송이다 |
| 이벤트 | 다른 애그리거트가 나중에 따로 맞추는 것 | OrderPlaced를 받아 재고를 줄이고 OrderCanceled를 받아 되돌린다 |
| 사가 | 따로 저장한 단계가 실패하면 앞 단계를 되돌리는 것 | OrderApplicationService의 결제하기가 거절되면 주문 취소하기로 보상한다 |
| 응용 서비스 | 꺼내고 시키고 저장하는 순서 | OrderApplicationService는 주문을 꺼내 주문에게 시키고 저장한다. 규칙은 갖지 않는다 |

## 고르는 순서

- 값 하나만 보면 되면 값 객체에 둔다
- 한 애그리거트의 칸만 보면 되면 애그리거트에 둔다
- 두 애그리거트 이상을 읽고 계산만 하면 도메인 서비스에 둔다
- 참 거짓 조건을 다른 조건과 묶어 쓰면 명세로 뺀다
- 다른 애그리거트가 따로 저장해도 되면 이벤트로 알린다
- 따로 저장한 단계를 실패 때 되돌려야 하면 사가로 보상을 잇는다
- 남는 것은 순서뿐이고 그 순서를 응용 서비스가 맡는다

## 사가

결제하기는 주문, 재고, 결제를 따로 저장한다.
그래서 한 번에 되돌릴 수 없다.

| 단계 | 맡는 곳 | 보상 | 보상을 맡는 곳 |
|---|---|---|---|
| 주문 접수 | OrderApplicationService의 주문하기 | 주문 취소 | OrderApplicationService의 주문 취소하기 |
| 재고 줄이기 | DecreaseStockHandler | 재고 되돌리기 | IncreaseStockHandler |
| 결제 | PaymentGateway | 실패하면 위 두 보상을 한다 | OrderApplicationService의 결제하기 |

- 보상은 끝난 일을 지우지 않고 반대 일을 한 번 더 한다
- 결제가 거절된 주문은 취소로 남는다
- 재고는 이벤트를 처리한 뒤에 맞춰진다
# 컨텍스트 맵

## 하위 도메인

| 하위 도메인 | 종류 | 왜 | 바운디드 컨텍스트 | 묶음 |
|---|---|---|---|---|
| 주문 | 핵심 | 주문, 결제, 배송, 취소 규칙이 이 가게가 잘해야 하는 일이다 | 주문 컨텍스트 | ddd.order |
| 상품 | 지원 | 주문에 쓸 상품과 재고를 맡는다. 가게에 맞게 직접 만든다 | 상품 컨텍스트 | ddd.catalog |
| 회원 | 일반 | 이름과 등급만 맡는다. 어느 가게나 비슷해서 사다 써도 된다 | 회원 컨텍스트 | ddd.member |
| 배송 | 지원 | 결제한 주문을 받을 곳으로 보낸다. 주문을 돕는다 | 배송 컨텍스트 | ddd.shipping |
| 결제 | 일반 | 돈을 받는 일은 어느 가게나 같다. 외부 결제 모듈을 사다 쓴다 | 외부 결제 모듈 | legacypay |

- 하위 도메인은 업무를 나눈 것이다
- 바운디드 컨텍스트(bounded context)는 한 모델과 한 말이 통하는 코드의 경계다
- 이 프로그램은 하위 도메인 하나에 컨텍스트 하나를 둔다
- 결제는 우리가 만들지 않는다. 외부 결제 모듈이 맡는다
- 컨텍스트 안에는 domain, application, infrastructure 계층을 둔다

## 공유 커널

- 돈 Money는 공유 커널(shared kernel) 묶음 ddd.shared에 둔다
- 주문과 상품 컨텍스트가 함께 쓴다
- 바꾸려면 쓰는 컨텍스트가 모두 합의해야 한다. 그래서 작게 둔다

## 컨텍스트 사이

| 쓰는 쪽 | 쓰이는 쪽 | 무엇 |
|---|---|---|
| 주문 | 상품 | 주문 항목 팩토리가 상품 저장소에서 상품 이름과 가격을 읽는다 |
| 주문 | 회원 | 할인 정책과 주문 응용 서비스가 회원과 회원 등급을 읽고, 주문 조회 서비스가 회원 이름을 읽는다 |
| 상품 | 주문 | 재고 줄이기 처리기가 주문 접수됨 이벤트를 받아 재고를 줄이고, 재고 되돌리기 처리기가 주문 취소됨 이벤트를 받아 재고를 되돌린다 |
| 배송 | 주문 | 결제 완료 메시지 처리기가 결제 완료 메시지 글자를 읽어 배송을 만든다 |
| 주문 | 외부 결제 | 결제 어댑터가 결제 금액을 외부 결제 모듈에 맡기고 받은 코드 글자를 결제 결과로 번역한다 |
| 주문, 상품 | 공유 커널 | 돈 |

- 같은 상품이라도 상품 컨텍스트의 상품은 지금 가격과 재고를 갖는다
- 주문 컨텍스트의 주문 항목은 주문 때의 상품 이름과 가격을 갖는다
- 주문과 상품은 다른 컨텍스트의 클래스를 import로 바로 쓴다
- 배송은 주문 컨텍스트의 클래스를 import하지 않는다. 주문의 공개 호스트 서비스가 보낸 메시지 글자만 읽는다
- 배송 컨텍스트의 배송은 주문 번호와 배송 주소를 자기 모양(숫자와 글자)으로 갖는다
- 주문 도메인과 응용 계층은 legacypay를 import하지 않는다. 외부 결제는 결제 어댑터로만 쓴다

## 공개 호스트 서비스와 발행된 언어

- 공개 호스트 서비스(open host service)는 한 컨텍스트가 바깥에 열어 둔 정해진 창구다
- 주문 컨텍스트의 창구는 OrderOpenHostService다. 결제하기가 끝나면 결제 완료 메시지를 이벤트 발행기에 넘긴다
- 발행된 언어(published language)는 그 창구가 쓰는 정해진 메시지 모양이다
- 메시지는 한 줄 글자다. 맨 앞은 종류, 그 뒤는 키=값이고 |로 나눈다
- 예: ORDER_PAID|orderId=1|address=서울시 강남구

| 칸 | 값 | 뜻 |
|---|---|---|
| 종류 | ORDER_PAID | 결제 완료 메시지 |
| orderId | 숫자 | 결제한 주문 번호 |
| address | 글자 | 배송 주소 |

- 받는 쪽은 주문 클래스를 몰라도 이 모양만 알면 읽는다
- 주문 컨텍스트는 안의 모델을 바꿔도 이 모양은 지킨다

## 부패 방지 계층

- 외부 결제 모듈 legacypay는 우리가 만들지 않았고 고칠 수 없다
- 외부 모듈은 우리와 다른 말을 쓴다. 영어 이름, 원 단위 int, 코드 글자
- 부패 방지 계층(anticorruption layer)은 바깥 모델의 말이 우리 모델로 새어 들지 않게 경계에서 번역하는 층이다
- 주문 컨텍스트의 부패 방지 계층은 결제 어댑터 LegacyPaymentAdapter다
- 주문 도메인과 응용 계층은 결제 창구 PaymentGateway와 결제 결과 PaymentResult만 안다
- 외부 모듈이 바뀌면 결제 어댑터만 고친다

| 외부 결제 모듈의 말 | 주문 컨텍스트의 말 |
|---|---|
| approve(merchantKey, amountWon) | 결제 창구의 pay(돈) |
| merchantKey 가게 키 | 결제 어댑터만 안다 |
| amountWon 원 단위 int | 돈 Money |
| 0000 | 승인 |
| E101 | 거절. 결제 한도를 넘었습니다 |
| 그 밖의 코드 | 거절. 결제에 실패했습니다 |
